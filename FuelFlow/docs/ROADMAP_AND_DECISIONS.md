# FuelFlow 路线与决策清单

## 阶段路线

### Phase 0: 产品和设计定稿

目标：
- 明确首发市场和默认单位。
- 确定 Dashboard、Add Fuel、Logs、Garage 的信息架构。
- 确定 MVP 数据字段和导出字段。
- 确定视觉系统基础色、字号层级和组件风格。

交付：
- 产品定位文档。
- 设计方向文档。
- 功能规格文档。
- 页面草图或 Figma 线框。

状态：
- 已完成初稿。
- 已生成 app icon、单个图标、页面插画和移动端概念图。
- 已进入 Phase 1 原型搭建，不再停留在纯讨论阶段。

### Phase 1: 本地可用 MVP

目标：
- 用户可创建车辆。
- 用户可添加加油记录。
- app 可计算油耗和月度油费。
- 用户可查看记录列表和车辆摘要。

当前状态：
- uni-app H5 工程已建立。
- Dashboard、Add Fuel、Logs、Garage、Reports、Settings 已有静态原型。
- Privacy Policy 和 Disclaimer 已有草案页面。
- 下一步重点是把静态原型推进为真实输入、本地数据和计算闭环。

不追求：
- 云同步。
- 支付订阅。
- 高级税务 PDF。
- OCR 或地图能力。

### Phase 2: 海外实用增强

目标：
- 完善 Business / Personal 统计。
- 完善 CSV 导出。
- 增加 Expense Log。
- 增加更灵活的单位和货币偏好。
- 增加基础数据备份能力。

### Phase 3: 留存和商业化

目标：
- 年度报告。
- 保养提醒。
- PDF 导出。
- 多设备同步。
- 高级报表或订阅权益。

## 当前建议的 MVP 取舍

| 模块 | 建议 | 原因 |
| --- | --- | --- |
| 多车辆 | 首版做 | 数据结构基础，后补会很痛 |
| 快速加油记录 | 首版做 | 核心刚需 |
| 油耗趋势 | 首版做轻量版 | 产品价值必须可见 |
| Business / Personal | 首版做 | 海外差异化核心 |
| Expense Log | 二期做 | 重要但可后置 |
| CSV 导出 | 首版设计字段，二期完善 | 先保证数据结构正确 |
| PDF 报告 | 后置 | 视觉成本和实现成本较高 |
| OCR 小票 | 后置 | 不是 MVP 核心闭环 |
| 云同步 | 后置 | 先验证本地体验 |
| Settings | 首版做基础项 | 单位、货币、导出偏好会影响数据口径 |
| Privacy / Disclaimer | 首版放入口和草案 | 海外工具类 app 上架前必须补齐 |

## 待决策事项

### D1: 首发市场

选项：
- 美国优先。
- 全球通用优先。

建议：
- 产品设计按全球通用保留单位能力，但默认文案和导出优先服务美国用户。

原因：
- 美国市场有明确 MPG、IRS、Gig Worker 场景。
- 过早做全球税务规则会稀释 MVP。

### D2: 默认单位

选项：
- mi / gal / MPG / USD。
- km / L / L/100km / 本地货币。
- 首次启动选择。

建议：
- 首次启动通过地区默认值自动建议，允许用户修改。

### D3: 首页结构

选项：
- 单车 Dashboard。
- 多车 Garage。

建议：
- 首页为当前车辆 Dashboard，顶部提供车辆切换。

原因：
- 大多数用户每次只关心当前车辆。
- Garage 作为管理页，不应抢占记录效率。

### D4: 快速录入方式

选项：
- 普通表单。
- 自定义数字键盘。
- 数字滚轮。

建议：
- MVP 先用大号数字输入和自动推导，后续再升级数字键盘或滚轮。

原因：
- 过早定制输入组件会增加实现风险。
- 体验重点是少字段、自动补全和默认值，而不是控件本身。

### D5: 商业模式

选项：
- 免费基础版 + 高级导出订阅。
- 一次性买断。
- 完全免费。

建议：
- 先按免费基础版 + 高级导出/高级报告预留，不在 MVP 阶段接入支付。

原因：
- 用户愿意付费的部分更可能是导出、报表、云同步和多设备，而不是基础记录。

## 设计讨论问题

1. FuelFlow 是否要保留“画廊极简”作为长期品牌方向，还是更偏专业财务工具？
2. 首页关键指标应展示 3 个还是 4 个？
3. Add Fuel 是否必须支持 5 秒内完成记录？
4. Business / Personal 是每笔记录必选，还是默认 Personal 并允许切换？
5. Expense Log 是否要和 Fuel Log 共用一套记录列表？
6. 是否需要中文界面，还是先坚持英文海外市场？
7. 年度报告是产品亮点，还是二期营销功能？

## 暂定结论

- README 的愿景方向成立，但需要避免过度概念化。
- 当前最关键的不是增加更多功能，而是把“快速记录 + 可信计算 + 可导出”打穿。
- 设计上应克制，首屏应像一个高质量工具，而不是宣传页。
- MVP 文档应先固定数据字段和计算口径，再进入界面实现。
- 当前实现应继续避免假手机壳、假状态栏和仅用于展示的浏览器包装。
- 每轮实现完成后应按视觉与验收清单进行真实截图、资源和构建检查。
